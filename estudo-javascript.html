01

DOM: selecionar e criar elementos

Tudo no app começa buscando referências pra elementos que já existem no HTML e, a partir delas, criando novos elementos dinamicamente. Essas duas operações aparecem em praticamente toda função do projeto.

catalogo.js
const containerGrade = document.getElementById("grade-filmes");
const card = document.createElement("article");
card.className = "card-filme";

getElementById busca um elemento já existente no HTML pelo atributo id — usamos isso uma vez, no início de cada módulo, pra guardar a referência numa constante (não precisa buscar de novo depois). createElement faz o oposto: fabrica um elemento novo, do zero, que ainda não existe em lugar nenhum da página até você anexá-lo com appendChild.

Template literals no lugar de concatenação

Pra montar o HTML interno de um card, usamos template literals (crase + ${'{'}...{'}'}) em vez de somar strings com +:

catalogo.js — criarCardFilme
card.innerHTML = `
  <div class="capa-placeholder">
    <span>${filme.titulo}</span>
    <span class="faixa-etaria">${filme.faixa}</span>
  </div>
`;

Isso permite quebrar linha livremente dentro da string e interpolar variáveis com ${'{'}expressao{'}'} sem precisar escapar aspas ou concatenar pedaço por pedaço. É a mesma sintaxe usada nas Promises simuladas do capítulo 06.

Duas formas de mexer no conteúdo de um elemento

.innerHTML interpreta a string como HTML de verdade (cria elementos filhos) — usado quando o conteúdo tem tags. .textContent trata tudo como texto puro, sem interpretar tags — mais seguro quando o valor pode vir de fora (evita que alguém injete HTML malicioso sem querer). No modal, preenchemos textos simples com .textContent (ex: modalTitulo.textContent = filme.titulo) e só usamos .innerHTML quando realmente precisamos gerar tags novas.

02

Eventos e closures

addEventListener liga uma função a um evento (clique, digitação, tecla) de um elemento. A parte mais sutil do projeto está em como essas funções "lembram" de valores específicos — isso se chama closure.

O que é uma closure

Uma closure é quando uma função guarda acesso às variáveis que existiam ao seu redor no momento em que foi criada, mesmo depois que a função externa já terminou de executar. Toda função em JavaScript forma uma closure automaticamente — não é algo que você "liga"; é o comportamento padrão da linguagem.

carrinho.js — renderizarCarrinho
for (const item of carrinho) {
  const linha = document.createElement("div");
  linha.innerHTML = `...`;

  linha.querySelector(".botao-remover-item").addEventListener("click", () => {
    removerDoCarrinho(item.idCarrinho); // "item" é lembrado por closure
  });

  carrinhoLista.appendChild(linha);
}

Se o carrinho tem 3 itens, esse loop cria 3 botões — e cada um recebe sua própria função de clique, que fechou (fez closure) sobre o item daquela iteração específica. Clicar no botão do item 1 remove o item 1; clicar no do item 3 remove o item 3 — mesmo os três botões executando literalmente o mesmo código-fonte.

A pegadinha clássica: var em loops

Isso só funciona porque o loop usa const. Com var, todas as iterações compartilhariam a mesma variável (var tem escopo de função, não de bloco) — os três botões acabariam removendo sempre o último item da lista, porque no momento do clique o loop já teria terminado e item apontaria pro valor final. Isso foi um bug real e comum em JS antes do ES6 introduzir let/const com escopo de bloco — cada iteração de um loop com let ganha sua própria cópia da variável.

Por que uma arrow function "vazia" na frente do listener

catalogo.js — criarBotaoCategoria
botao.addEventListener("click", () => selecionarCategoria(nome));

Se fosse escrito addEventListener("click", selecionarCategoria), o clique passaria o objeto do evento como argumento pra selecionarCategoria — não o nome da categoria. A arrow function intermediária existe só pra "prender" o valor certo de nome e chamar a função com o argumento certo.

stopPropagation — parar um evento de "borbulhar"

catalogo.js — botão de favorito dentro do card
card.querySelector(".botao-favorito").addEventListener("click", (evento) => {
  evento.stopPropagation();
  alternarFavorito(filme.id, renderizarFilmes);
});

card.addEventListener("click", () => abrirModal(filme));

Por padrão, um clique num elemento filho também dispara os listeners dos elementos pais (o evento "borbulha" — bubbling — subindo pela árvore do DOM). O coração está dentro do card, e o card inteiro tem um listener que abre o modal. Sem stopPropagation(), clicar no coração também abriria o modal do filme — porque o clique borbulharia do botão até o card.

03

Arrays funcionais: filter, find, sort

Três métodos de array carregam praticamente toda a lógica de dados do catálogo. Nenhum deles modifica o array original por conta própria (exceto sort, que é a exceção importante).

.filter() — pegar vários, os que servem

catalogo.js — renderizarFilmes
filmes.filter((filme) => {
  const passaCategoria = categoriaAtual === "Todos" || filme.generos.includes(categoriaAtual);
  const passaBusca = termo === "" || normalizarTexto(filme.titulo).includes(termo);
  const passaFavoritos = !somenteFavoritos || ehFavorito(filme.id);
  return passaCategoria && passaBusca && passaFavoritos;
});

Percorre o array original e devolve um array novo, só com os itens em que a função passada devolveu true. O mesmo mecanismo serve pra excluir, invertendo a condição — é como removemos um item do carrinho: carrinho.filter(item => item.idCarrinho !== idCarrinho) ("mantenha todos, menos esse").

.find() — pegar um só, o primeiro que serve

modal.js — confirmarAluguel
const agenciaEscolhida = AGENCIAS.find((a) => a.id === Number(selectAgencia.value));

Primo do filter, mas devolve só o primeiro elemento que bate na condição (ou undefined, se ninguém bater) — não um array. selectAgencia.value vem como string do HTML (todo valor de formulário é texto), por isso o Number(...): sem essa conversão, "1" === 1 é false, e o find nunca acharia a agência certa.

.sort() — a exceção que muda o array original

catalogo.js — ordenarFilmes
function ordenarFilmes(lista, criterio) {
  const copia = [...lista]; // cópia — sort() muta o array original!

  switch (criterio) {
    case "preco-asc":
      return copia.sort((a, b) => a.valor - b.valor);
    case "nome":
      return copia.sort((a, b) => a.titulo.localeCompare(b.titulo, "pt-BR"));
    default:
      return copia;
  }
}
Por que a cópia com [...lista]

Diferente de filter e find, .sort() reordena o array original, no lugar (não cria um novo). Se ordenássemos filmes diretamente, o catálogo inteiro ficaria embaralhado permanentemente na primeira ordenação, mesmo depois de voltar pra "Todos". O spread [...lista] cria uma cópia rasa antes de ordenar, protegendo o array original.

Outro detalhe: .sort() sem função de comparação ordena convertendo tudo pra texto — [1, 100000, 21, 30, 4], não numericamente. Por isso toda chamada aqui passa uma função (a, b) => a.valor - b.valor: negativo significa "a vem antes", positivo "a vem depois", zero "mantém a ordem". Pra nomes, localeCompare entende acentuação do português (ordena "Á" perto de "A", como um dicionário faria).

04

Formulários e captura de texto

Dois padrões se repetem sempre que o usuário digita ou escolhe algo: ler o valor no evento certo, e normalizar texto antes de comparar.

catalogo.js
campoBusca.addEventListener("input", (evento) => {
  termoBusca = evento.target.value; // dispara a cada tecla digitada
  renderizarFilmes();
});

selectOrdenar.addEventListener("change", (evento) => {
  criterioOrdenacao = evento.target.value; // dispara só ao trocar de opção
  renderizarFilmes();
});

"input" dispara a cada caractere digitado (bom pra busca em tempo real); "change" só dispara quando o valor é confirmado — no caso de um <select>, quando uma opção diferente é escolhida.

Normalizando texto pra busca

utilitarios.js
export function normalizarTexto(texto) {
  return texto
    .toLowerCase()
    .normalize("NFD")
    .replace(/[̀-ͯ]/g, "");
}

.normalize("NFD") decompõe caracteres acentuados em letra-base + marca de acento separada (ex: "ç" vira "c" + uma marca de cedilha, como dois caracteres Unicode distintos). O regex /[̀-ͯ]/g apaga qualquer caractere nessa faixa Unicode, que é exatamente onde vivem as "marcas de acento combinantes" — sobra só a letra-base. É assim que digitar "acao" encontra "Ação".

05

localStorage

Três coisas persistem entre visitas: o carrinho, os favoritos e a preferência de tema — todas guardadas no localStorage do navegador.

carrinho.js
function salvarCarrinho() {
  try {
    localStorage.setItem(CHAVE_CARRINHO, JSON.stringify(carrinho));
  } catch (erro) {
    console.warn("Não foi possível salvar o carrinho no localStorage.", erro);
  }
}

Por que só aceita string

localStorage é, por baixo, um dicionário chave→valor onde tanto a chave quanto o valor são sempre texto — não existe "tipo array" ou "tipo objeto" salvo ali. Isso é proposital: o formato foi desenhado pra ser trivial de persistir em disco de forma consistente em qualquer navegador. Salvar um array direto (sem JSON.stringify) não dá erro — o JS silenciosamente chama .toString() nele, e o valor salvo vira algo como "[object Object],[object Object]", perdendo os dados de verdade.

Origem e escopo

localStorage é isolado por origem — protocolo, domínio e porta juntos. http://site.com e https://site.com têm storages completamente separados, mesmo sendo "o mesmo site" pro usuário. É também por isso que os dados nunca saem do navegador de quem está usando: não sincronizam entre dispositivos nem ficam visíveis pra outra pessoa — só um backend real resolveria isso.

Por que o try/catch é necessário, não decorativo

A API pode lançar SecurityError em cenários reais: armazenamento bloqueado por política do navegador, cota excedida, ou certas configurações de aba anônima. Sem o try/catch, um erro aí quebraria a execução de toda a função que chamou salvarCarrinho() — com ele, o site continua funcionando normalmente, só sem persistir daquela vez.

Set ↔ Array, na ida e na volta

favoritos.js
let favoritos = new Set();

// salvar: Set não é serializável direto, vira array primeiro
localStorage.setItem(CHAVE_FAVORITOS, JSON.stringify([...favoritos]));

// carregar: array volta a virar Set
favoritos = new Set(JSON.parse(salvo));

Favoritos usa Set (conjunto) em vez de array, porque um filme só pode estar "favoritado" ou não — não faz sentido duplicar. Set tem .has(), .add() e .delete() prontos pra essa checagem de pertencimento. Mas JSON.stringify não sabe serializar um Set diretamente — por isso o espalhamento [...favoritos] converte pra array antes de salvar, e new Set(array) reconstrói o conjunto ao carregar.

06

Promises e async/await

Simulamos uma chamada de API — o formato exato que o backend real vai assumir depois — pra já deixar o app preparado pra trocar dados fixos por dados de rede sem reescrever a lógica de exibição.

movies.js
export function buscarFilmes() {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve(FILMES);
    }, 600);
  });
}

Os três estados de uma Promise

  • pending (pendente) — ainda não terminou
  • fulfilled (cumprida) — terminou com sucesso, carrega um valor
  • rejected (rejeitada) — terminou com erro

new Promise((resolve, reject) => ...) roda essa função imediatamente, de forma síncrona. Chamar resolve(valor) transiciona pra fulfilled; chamar reject(erro) transicionaria pra rejected (não usamos isso ainda, porque a API é simulada e nunca falha — mas é o mesmo lugar onde um fetch real trataria "servidor fora do ar"). Uma vez decidido, o estado nunca muda de novo.

await, dentro de uma função async

catalogo.js — iniciarCatalogo
export async function iniciarCatalogo() {
  carregarFavoritos();
  mostrarCarregando();
  filmes = await buscarFilmes();
  selecionarCategoria("Todos");
}

await só existe dentro de uma função marcada async. Ele pausa aquela função específica até a Promise resolver, e entrega o valor resolvido direto — sem precisar de um callback .then(). Por causa disso, iniciarCatalogo lê como código sequencial normal, de cima a baixo, mesmo tendo uma pausa assíncrona no meio.

"Pausar" não trava o navegador

Enquanto iniciarCatalogo está parada no await, o event loop do navegador continua livre pra atender outras coisas — cliques, hover, outros scripts. A prova prática: enquanto a mensagem "Carregando catálogo..." está na tela, o botão de tema (🌙) continua respondendo normalmente. Se await travasse a thread principal, esse clique ficaria congelado até os 600ms passarem.

Toda função async devolve uma Promise

Mesmo sem um return new Promise(...) explícito, qualquer função marcada async sempre devolve uma Promise — se ela tivesse return "pronto", quem chamasse a função receberia uma Promise que resolve pra "pronto", não a string direto.

Como isso viraria uma chamada real

o que buscarFilmes() vira quando o backend existir
export async function buscarFilmes() {
  try {
    const resposta = await fetch("http://localhost:8000/filmes/");
    return await resposta.json();
  } catch (erro) {
    throw new Error("Não foi possível carregar o catálogo.");
  }
}

fetch() devolve uma Promise — a "demora" deixa de ser um setTimeout fake e passa a ser o tempo real de ida e volta pela rede. resposta.json() também é assíncrono (ler e decodificar o corpo da resposta leva tempo), por isso o segundo await. Nada no resto do catalogo.js precisaria mudar — ele já está preparado pra "esperar".

07

Módulos ES (import/export)

Quando o projeto cresceu (catálogo, modal, carrinho, favoritos, tema, tudo num app.js só), dividimos em arquivos menores usando o sistema de módulos nativo do JavaScript.

favoritos.js exporta →
export function ehFavorito(idFilme) {
  return favoritos.has(idFilme);
}

export function alternarFavorito(idFilme, aoMudar) { /* ... */ }
catalogo.js importa ←
import { carregarFavoritos, ehFavorito, alternarFavorito } from "./favoritos.js";

O que muda em relação a scripts normais

Script clássicoMódulo (type="module")
Tudo cai no escopo global — variáveis de um arquivo "vazam" pros outrosCada arquivo tem seu próprio escopo isolado; só o que é exportado fica visível fora
Ordem dos <script> no HTML decide o que existe primeiroO import declara explicitamente a dependência — o navegador resolve a ordem sozinho
Modo "solto" por padrão (permite erros que módulos não permitem)Sempre em modo estrito automaticamente
Funciona abrindo o arquivo direto (file://)Exige servidor HTTP — bloqueado em file:// por segurança (CORS)
Por isso o servidor local

Foi essa última linha da tabela que nos obrigou a rodar python -m http.server e abrir o site por http://localhost:5500/... em vez de dar duplo clique no index.html. O navegador recusa buscar módulos de origem file:// por política de segurança — mesma família de proteção do CORS que vimos no backend de gastos.

Evitando importação circular

favoritos.js não importa nada de catalogo.js — mesmo precisando disparar um re-render depois de favoritar algo. Em vez disso, alternarFavorito recebe uma função de callback (aoMudar) como argumento:

catalogo.js chamando favoritos.js
alternarFavorito(filme.id, renderizarFilmes); // passa a função, não importa o módulo de volta

Isso mantém a dependência numa única direção (catalogo → favoritos, nunca o contrário). Duas dependências que se importam mutuamente ao mesmo tempo é um dos poucos jeitos reais de quebrar módulos ES — o grafo de dependências precisa ser resolvido antes de qualquer código rodar, e um ciclo síncrono impede isso.

app.js — de tudo pra quase nada

app.js, o arquivo inteiro
import { iniciarCatalogo } from "./catalogo.js";
import { iniciarCarrinho, fecharCarrinho } from "./carrinho.js";
import { iniciarTema } from "./tema.js";
import { fecharModal } from "./modal.js";

document.addEventListener("keydown", (evento) => {
  if (evento.key === "Escape") {
    fecharModal();
    fecharCarrinho();
  }
});

iniciarCarrinho();
iniciarTema();
iniciarCatalogo();

O arquivo que antes concentrava tudo virou só o "montador": importa cada pedaço já pronto e liga as três inicializações. É a diferença entre saber como cada parte funciona e saber como as partes se encaixam — e esse arquivo só precisa da segunda coisa.

08

O padrão geral por trás de tudo

Sem perceber, o mesmo ciclo de três passos se repete em toda funcionalidade do projeto — categoria, busca, favoritos, ordenação, carrinho:

  1. Estado vive em variáveis (categoriaAtual, termoBusca, carrinho, favoritos)
  2. Uma ação do usuário muda o estado (clique, digitação, seleção)
  3. Uma função de "renderizar" lê o estado atual e redesenha aquele pedaço da tela do zero — sempre limpando (innerHTML = "") antes de recriar, nunca tentando atualizar só o que mudou

Isso é, em miniatura e escrito à mão, a mesma ideia central que frameworks como React resolvem de forma automática — a diferença é que lá existe um mecanismo (o "virtual DOM") que decide sozinho o que precisa mudar de verdade na tela; aqui, cada re-render recria tudo, o que é mais simples de entender mas mais caro computacionalmente. Pra um catálogo de 16 filmes, essa diferença de custo é irrelevante — só passaria a importar em listas muito grandes ou atualizações muito frequentes.
